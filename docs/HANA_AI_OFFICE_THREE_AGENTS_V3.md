# HANA AI OFFICE｜三大自主 Agent 需求基準 V3
更新：2026-10-26（Asia/Taipei）
適用：h-s017/hana-focus（現有專案）；後端：既有 hana-ai-office Supabase。本文為「實作需求／驗收基準」，不是已部署聲明。

## 唯一產品入口與自主級別
- HANA FOCUS 是唯一管理入口，不另做三個彼此分離的後台。既有資料、預約網站與日曆維持單一來源。
- 僅保留 3 個主要角色：Social Editor（社群小編）、Secretary（秘書）、Project Manager（專案經理）。
- 三者內部工作採「自動執行、無逐項人工核准、創辦人隨時可改」；每次執行保留時間、來源、狀態、Canva URL、錯誤和版本。不得以 review / approved 狀態作為內部排程的必要關卡。
- **內部產出 ≠ 公開發布或交付客戶**。沒有額外指令不自動發布 Instagram、外寄客戶成果、不替客戶修改既有已確認預約時間、不更動客戶核准版本、不自動付款。
- 保留具風險操作的安全閘：資料來源缺失、客戶衝突、未授權 API、權限失效、付費資源或版本矛盾時標記 blocked 並通知，不自行假設。
- 不啟用任何未核准的付費 API / 方案；必要時先顯示成本與替代方案。不可將秘密、個資或未公開客戶文件提交公共 GitHub。

## 01 Social Editor｜每日香氛微課
觸發：Asia/Taipei 每天固定排程（沿用既有 GitHub Actions 00:10 UTC/08:10 台灣時間，可於後台修改），並提供「立即重製」。
輸入：365 天主題庫、已用主題清單、參考來源、品牌視覺規範、Canva template_id。
輸出：每日 **1 個教學主題**、5–8 張 Instagram 4:5（1080×1350；預設 6 張）的單一 Canva 多頁設計；繁體中文分層可編輯文字、每頁獨立圖像、一篇 caption/hashtags/alt text、核對來源及推薦 1 首古典樂曲。直接保存在創辦人可編輯的 Canva 內部資料夾，儲存設計 ID、編輯 URL 及執行紀錄；**不用創辦人先審**。
視覺：每日可更換風格，但同日全部頁面只有一套一致風格。無人物／器官、無柑橘，不使用過量樹葉光影、重複香水瓶或他人照片；除非另獲明確授權，不讀取私人照片素材庫。背景圖不含 AI 文字，中文與排版須為真正可編輯的 Canva 元件。
質檢：事實／來源、尺寸、頁數、語言、溢字、無重複、版權與禁用元素。失敗不得假裝設計完成；通知後可安全重試。
Canva 執行：以已完成資料欄位標記的 Canva Brand Template / design 配合 Autofill API；先取得獨立 Canva Developer OAuth 授權，金鑰與 Refresh Token 只存在後端，不可假定 ChatGPT 內的 Canva 連線能由排程重用。現有模板 data set 為空，需建立可填欄位而非宣稱已完成自動化。
IG 「直接自動做 Canva 草稿」不等同 Instagram 自動發布，後者未列入此版本需求。

## 02 Secretary｜課程預約與行程
來源真相：現有 Google Calendar 主日曆（授權業主） + reservation.hanascent.com 的實際公開場次、時段、容量與訂單。不得建立第二套平行可編行事曆，不得臆測課時、緩衝時間或空檔。
工作：新預約、取消或改期事件同步；有任何新行程時重新核對未來開放場次，防止撞期與超收；新增已確認預約到 Google Calendar；更新預約平台的可預約日期；即時向創辦人通知新預約、取消、異動、衝突、失敗。創辦人從 HANA FOCUS 或 Calendar 能修改，修改後再反映至預約網站。
預約安全：空檔自動封鎖可用場次；既有客戶確認的訂單不可靜默取消或搬動，只標記 urgent conflict、通知創辦人並保留原事件。新增場次必須符合創辦人明確設定之上課規則和來源資料，不得用「未看到 Google 行程」推論可以公開預約。
每月最後 5 個曆日，按照創辦人既定課表規則生成下個月的內部月曆與建議開放日期；若已授權自動開放則可同步，否則保持已有的正式場次。支援特殊例外，不硬編「所有週末都不開課」以致覆蓋已確認週末活動。
技術：Google Calendar OAuth + events.watch（通知頻道需續期）及定期增量同步；Reservation 後端驗證寫入、webhook/輪詢、idempotency keys、去重、重試及可稽核的變更紀錄。網站 / API 憑證不可用 ChatGPT 的日曆連線代替。若來源驗證失敗，維持現有正式場次不覆寫。
通知：優先依使用者已授權且能驗證送達的管道；後台顯示通知送達狀態與事件連結。客戶通知與業主通知須分開處理，不能預設已發送。

## 03 Project Manager｜從規格到內部 Canva 交付
觸發：創辦人在 HANA FOCUS 輸入專案規格或導入客戶已提供的檔案；可按「自動產生」或選擇監測變更後自動更新。
輸入必需欄位：專案名稱、目的、範圍、排除事項、交付清單、核准版本與引用來源、指定 Canva 範本/尺寸、期程或空值。
流程：辨識範圍與版本 → 建立 hana_projects/hana_tasks 的專案與里程碑 → 生成可追溯的策略、清單、文案與交付頁面 → 對應 Canva 指定格式，產出多頁可編輯內部設計 → 回寫內部設計 ID/可編輯 URL、狀態及版本。**內部交付免逐步審查**。
創辦人後續可以直接在 Canva 編輯；系統不得覆蓋使用者最近一次手動修改。重製需建立新版本或經明確操作覆寫。設計差異、未核實歷史、金額、色號和商標使用權需明確標註來源與確信狀態；不可把 AI 草稿寫成客戶已核准定稿。
文慶雞（方案 B）可用於驗收，但不得超出既有版範圍；不重開已被移除之包裝／制服工作。此 Agent 的內部文件交付不等於正式向客戶交件。
設計模板由創辦人逐專案指定；不要強制所有客戶共用單一版式。

## 共用平台／現有程式遷移
- 維持現有 Supabase 專案、Auth、RLS、hana_tasks/hana_task_runs/hana_automation_events/hana_projects 等，不建立新 Supabase 專案或平行任務 DB。
- 現有 hana-agent/ hana-automation 和 GitHub Actions 社群草稿排程，逐步改成 3 個實際執行器；原「Brand Strategist／Creative Producer」可作為 PM 的內部處理步驟，不再出現在主控制台作為獨立 Agent。
- 後台每張 Agent 卡：啟用／暫停、上次執行、下次排程、成功／失敗、最後產出、Canva 編輯連結、通知紀錄、立即重試、修改設定。秘書卡另含月曆、預約場次／衝突、手動覆寫與同步狀態。
- 以事件作業佇列、獨立 retry/dead-letter、idempotency key、限流、Webhook 簽章驗證、憑證更新、RLS、使用者可編權限及版本管理構成基礎。阻止同日重複執行產生重複貼文、重複預約及重複專案。
- UI 顯示狀態 truthfulness：未授權、已排程、執行中、已交付 Canva、已通知、失敗、需人工處理，不可顯示假的成功或自動交付。

## 實作順序（Codex）
1. 盤點既有 repo、正式分支、現有 PR、Supabase schema、主日曆與 reservation 的後端讀寫接口。保留既有備份、scope guard、功能與 CI。
2. 建立共用任務執行、排程、通知、設定及審計架構；先用不涉及實際客戶資料的 sandbox fixtures 寫整合測試。
3. Social Editor：修復每日排程、建立 Canva 可填欄位的 6 頁母版、OAuth/Autofill、可編交付、QA、失敗重試；實測連續兩次排程且不需人工批准。
4. Secretary：Calendar/Reservation 真實 API 授權與事件對帳，新增預約自動通知與阻擋衝突；已有客戶訂單永不被靜默改期；月底五天月曆草稿；可在後台人工修正。
5. Project Manager：規格表單、版本／範圍校驗、專案與任務自動生成、使用指定 Canva 母版自動輸出內部文件、回填可編連結和修訂版本。
6. 將新卡片整合進現有 HANA FOCUS；提供逐一啟用/暫停開關；核對所有流程後才切換真實排程。生產切換應遵守既有 release guard。
7. 將欠缺的 OAuth/API 授權與任何新增付費費用在後台明確呈現。不能測試成功前不得宣稱已上線。

## 最小驗收條件
- 每日排程真正新增一份不同主題、5–8 頁的 1080×1350 可編輯 Canva 輪播，有對應的內部連結，無審核阻塞。
- Google 日曆新增占用後，對應可預約場次自動封鎖；新客戶有效預約雙向反映並通知業主；任何衝突可被業主覆寫且可回復。
- 輸入一份具版本的專案規格後，在 HANA FOCUS 出現專案、任務與指定格式的 Canva 可編輯交付稿，無逐階批准。
- 身分驗證、資料範圍、重複事件、OAuth 過期、Canva 失敗、月末跨月、時區及手機 UX 有自動測試與真實執行證據。
- 任何步驟不可把「GitHub 文字草稿」冒充「Canva 已交付」，不可將「內部稿」冒充「對客戶正式完稿」。
